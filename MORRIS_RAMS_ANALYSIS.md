## 2. Complete Workflow — What Happens From Open to Downloaded PDF

### Step 1 — Route resolution
User clicks the RAMS tile (Dashboard, sidebar, favourites, "recommended for {trade}", or command palette).
- If the link is `/app/tool/rams`, `GenericToolPage.jsx` catches it and renders `<RedirectTo path="/app/rams" />`.
- The canonical route `/app/rams` renders `<ProfileGate><Rams /></ProfileGate>`. `ProfileGate` blocks access until the user has completed the mandatory profile fields (fullName, address, etc.).

### Step 2 — Form loading & defaults
`Rams.jsx` mounts. Each state field initialises to:

| Field | Default |
|---|---|
| `documentRef` | `""` (a fallback `RAMS-YYYYMMDD-001` is generated on export if still blank). |
| `documentRevision` | `"Rev 1"`. |
| `revisionHistory` | Single row `{rev:"Rev 1", date: today, description:"Initial issue", author:""}`. |
| `operativesCount` | `2`. |
| `workAtHeight` | `false`. |
| `overallRiskRating` | `"Medium"`. |
| `personsAtRisk` | `["Site operatives"]`. |
| `training` | `["CSCS"]`. |
| `hazards` | `[newHazard()]` → 1 empty row: `Inhalation`, `L=3, S=3` before / `L=1, S=3` after. |
| `notCovered` | `"Hot works, confined space, live electrical work, asbestos disturbance"`. |
| Every free-text section (siteInduction, manualHandling, noiseAndVibration, keepingSiteTidy, fireEvacuation, sharedWith, clientSignOff*, reviewSchedule, welfare*, env*, sequence, firstAiderName, assemblyPoint, emergencyContacts, ppeOverrideNote) | Empty string. |
| `ppe`, `equipment`, `coshh` | Empty arrays. |
| `liveSignature` | Empty string (falls back to `user.signature` from profile). |

### Step 3 — Profile hydration
`useAuth()` gives the component the current user. Trade-personalisation is applied by `manualHandlingPlaceholder = getManualHandlingPlaceholder(user?.trade)` (line 222). The Manual Handling section shows a gold *"Personalised for {trade}"* pill on line 679.

### Step 4 — Draft resume (optional)
On mount, `Rams.jsx` reads the `?draftId=` query param. If present:
1. `fetchDraft(id)` → GET `/api/drafts/{id}`.
2. If the draft matches `toolId === "rams"`, every field on `d.data` is restored with per-field guards so older drafts that lack a key don't wipe current state.
3. Toast: "Draft restored". Query param is cleared with `clearDraftQueryParam()`.

### Step 5 — User completes the form
The user can:
- Fill Document Control, Scope of Works and every free-text section.
- Add revision rows via `addRevision` (auto-authored with `user.fullName`).
- Add hazards via `addHazard`. Each hazard row exposes:
  - `Exposure route` (9 options)
  - `Hazard or substance name`
  - `Activity that causes the exposure`
  - Multi-select **Persons affected**
  - `Likelihood before` (1–5), `Severity before` (1–5) → live **Risk before** badge
  - `Likelihood after`, `Severity after` (defaults to `severityBefore`; lowering it triggers a `window.confirm` and sets `severityManualOverride: true`)
  - `Controls` textarea (one per line)
  - A live "Plain-language line" preview computed by `composeHazardLine()`
- Toggle PPE and equipment via `CheckboxRow`. Suggestions appear in gold-bordered cards driven by `PPE_RULES` / `EQUIP_RULES`. Example rule (l.92): `Inhalation` OR keyword `dust|cutting|drilling|grinding` → suggests `"RPE — dust mask or respirator"` with reason `"Dust or cutting in the air"`.
- Add COSHH substances via `addCoshh`. Ticking `licensedSeparate: true` gives the row a red border and warning banner.
- Draw or reuse a `Prepared by` signature via `LiveSignatureBlock`.
- Optionally sign the Client / Principal Contractor block.
- Save a draft any time via `DraftSaveButton`.
- Toggle favourite via the ★ button (updates `user.favourites` on the backend).

### Step 6 — Automatic calculations (live, in the UI)
- **Risk score** = Likelihood × Severity, rendered by `RatingBadge` with palette derived from `ratingFromScore()`.
- **Section numbering** is regenerated on every render by the `sn()` counter (l.490). If a section is hidden, the visible numbering stays consecutive.
- **PPE / Equipment suggestions** and **mismatch list** recompute via `useMemo` on every keystroke.

### Step 7 — Pre-export validation gate (`onDownload`, l.395)
Nothing leaves the page until *every* rule passes. Missing items are collected into a `missing[]` array and, if any exist, the export is aborted and a red `MissingBanner` is displayed with the exact list.

Validation rules currently enforced:
1. `user.fullName` must be set (Profile).
2. Either `user.signature` (Profile) or `liveSignature` (this page) must be set.
3. `task` must be non-empty.
4. At least one hazard row must have both `hazard` and `activity` filled.
5. **Every** hazard row must have `exposureRoute` + `hazard` + `activity`.
6. Every COSHH row must have `exposureRoute` + `substance` + `activity`.
7. If `ppeSuggestions` produced any PPE that is not ticked, the user must either tick it or supply a non-empty `ppeOverrideNote`.

### Step 8 — Data payload assembly (l.438–468)
On successful validation, a plain-JS `data` object is composed with every field. A local `userWithSig` variant is built so that a same-session `liveSignature` beats the profile signature.

### Step 9 — PDF generation (`downloadRamsPdf` → `generateRamsPdf`)
Everything happens **client-side, in-browser**, using jspdf. **There is no AI call.** No `/api/generate`. No LLM. The document is deterministic given the inputs.

`generateRamsPdf` walks a fixed section list, drawing each via the primitives (§1.3). A running `state.sectionNum` counter numbers sections. Layout is A4 portrait (595.28 × 841.89 pt), 48 pt margins, Helvetica.

**Header:** `drawHeader()` draws the company logo (or Morris "M" fallback), uppercase company name, today's date (en-GB), gold rule, and — on page 1 — the title `RAMS — <task>`.
**Footer:** `addFooter()` draws `Ref: <docref> · <today> · <user>` and the fixed Morris attribution line.

Section order actually produced by `rams-pdf.js` (with the current auto-numbering):

1. Document Control (kv-table: ref, revision, issue date, review date = today+1yr, prepared by, supervisor, client, principal contractor, site address)
2. Revision History (Rev / Date / Description / Author table)
3. Scope of Works (task, duration, operatives, WAH, overall rating)
4. Legislation (8 fixed statutes — see §4)
5. Persons at Risk (bullets)
6. Training and Competence (bullets)
7. Site Induction (paragraph — a hardcoded default appears if the user left it blank)
8. Risk Matrix Key (three sub-tables: Likelihood, Severity, Score → Rating → Action)
9. Risk Register Summary (Hazard / Initial / Residual, colour-filled per rating band)
10. Hazard Detail and Control Measures (per hazard: kv-table of all fields + bulleted controls)
11. Control Measures and PPE (bullets + optional Override note)
12. Manual Handling (only if the user filled the field)
13. Noise and Vibration (only if the user filled the field)
14. Plant and Equipment (bullets + fixed sentence: "All plant and equipment listed above has been checked and is in date.")
15. COSHH (standard-use substances table only)
15a. Substances Requiring a Separate Licensed Assessment (only if any COSHH row has `licensedSeparate: true`; sub-numbered via `suffix:"a", noIncrement:true`)
16. Permits and Authorisations (echoes `notCovered` + boilerplate stop-work paragraph)
17. Sequence of Operations (numbered list; if blank prints "To be completed by supervisor before works start.")
18. Keeping the Site Tidy (only if filled)
19. Work at Height (branch: with-controls paragraph, or "No work at height on this task.")
20. Welfare Arrangements (kv-table)
21. Environmental Considerations (kv-table)
22. Emergency Procedures (kv-table + parsed Role/Number contact table)
23. Fire and Emergency Evacuation (only if filled)
24. Who This RAMS Has Been Shared With (only if filled — parses "Name, Company, Role" per line into a real table)
25. Client / Principal Contractor Sign-Off (only if any of Name/Role/Date/Signature is present; stamps the client signature image)
26. Reviewing This RAMS (only if filled)
27. Briefing and Sign-Off (fixed intro paragraph + blank Print Name / Signature / Date table sized to `max(6, operativesCount)` rows)
28. `Prepared by` subheading (not numbered) with author kv-table (Name / Role / Company / Date) and the stamped signature image.

Visible section numbers therefore range from 1 through however many optional sections were filled (typically 20–27).

### Step 10 — Save & notify (after PDF export succeeds)
1. `saveToolData("rams", [{ id: uuid, title: task, reviewDueDate: today+1yr }])` — writes a record to `localStorage["morris_tool_data_v1"].rams` so future analytics/alerts have context.
2. `fireToolNotification({ toolId: "rams", toolName: "RAMS" })` — pushes a `safety`-category notification into the Notification Bell: *"RAMS generated — remember to communicate to all workers before works begin"*.
3. Sonner toast: `"RAMS PDF exported."`

### Step 11 — No document-history save
Because the RAMS pipeline never touches `/api/generate` or `/api/documents/save`, **the generated RAMS PDF does NOT appear in the user's Document History**. It only ever lives in the user's Downloads folder and inside the local Drafts store if they saved a draft. (See §5, gap G4.)

## 3. AI Prompt — Full Inventory

### 3.1 Reality check
**The RAMS tool does NOT use AI.** The runtime flow (§2) is: form → client-side jspdf. There is no LLM call.

However, a legacy AI prompt exists in the tool registry. Any AI-focused audit needs it, because it represents Morris's earlier intent for the RAMS tool and is still present in the codebase. It is also used *indirectly* — the backend `/api/generate` endpoint applies extra rules whenever the tool ID is "rams" (via `SINGLE_SIGNOFF_TOOLS` membership and via the RAMS-in-header trigger phrase). Those rules would fire only if someone called `/api/generate?tool=rams` directly.

### 3.2 The legacy user-facing prompt template
File: `/app/frontend/src/lib/tools-config.js` (l.111–127). Reproduced verbatim:

> Produce a full UK RAMS (Risk Assessment and Method Statement) document. Use the user's profile for company name, address, contact and trade (auto-populated). Include all of the following sections, each clearly labelled:
> 1. DOCUMENT CONTROL — document reference (use the supplied reference), document revision number (use the value supplied, or default to 'Rev 1' if blank), issue date (today), review date (today + 12 months), prepared by (full name from profile), supervisor / competent person (use the value supplied), client name, principal contractor name, full site address.
> 2. SCOPE OF WORKS — task, estimated duration, number of operatives, work at height yes/no, overall risk rating (use the value supplied).
> 3. LEGISLATION — explicitly cite ALL of: Management of Health and Safety at Work Regulations 1999; Manual Handling Operations Regulations 1992; COSHH Regulations 2002; PUWER 1998; Personal Protective Equipment at Work Regulations 1992; Work at Height Regulations 2005; Control of Noise at Work Regulations 2005; CDM 2015.
> 4. PERSONS AT RISK.
> 5. HAZARD AND RISK MATRIX — for EACH hazard supplied produce a row with columns: Hazard / Likelihood (1-5) / Severity (1-5) / Risk Score (LxS) / Risk Rating (Low/Medium/High) / Control Measures / Residual Score / Residual Rating. Use the overall risk rating supplied as guidance for the inherent rating before controls.
> 6. CONTROL MEASURES AND PPE — list the PPE required.
> 7. SEQUENCE OF OPERATIONS — produce the supplied step-by-step method statement as a numbered list. Each step on its own line. If the user did not supply one, leave a placeholder line stating 'To be completed by supervisor before works commence.'
> 8. PLANT AND EQUIPMENT — list every item to be used. State: 'All plant and equipment listed above has been inspected and is in date.'
> 9. COSHH — list any hazardous substances in use and state: 'COSHH assessments are available on request.' If none, write 'No hazardous substances in use on this task.'
> 10. WORK AT HEIGHT — if yes, summarise rescue plan, harness inspection regime and reference to a separate Working at Height Rescue Plan document. If no, write 'No work at height activities on this task.'
> 11. WELFARE ARRANGEMENTS — toilets, washing facilities, rest area, drinking water location on site.
> 12. ENVIRONMENTAL CONSIDERATIONS — waste disposal method, dust and noise impact, working hours, spill management.
> 13. EMERGENCY PROCEDURES — first aider name on site, assembly point location, nearest A&E, 999 contact. Also list every emergency contact number supplied by the user in a clean two-column table (Role / Number).
> 14. BRIEFING AND SIGN-OFF — table for each operative to print name, sign and date confirming they have been briefed on this RAMS.
> Close with a 'PREPARED BY' block (full name from profile, company, signature line, today's date) and a 'REVIEWED BY' block.
> Use only UK English. Do not use placeholder text. Use today's date and the auto-populated profile values throughout.

### 3.3 System-level rules that would wrap the template if `/api/generate` were called for RAMS
Assembled dynamically inside `/app/backend/server.py` around l.680–780:
- **Plain English rule (banned words):** the backend replaces/strips consultant words such as *facilitate, utilise, endeavour, kinetic, prior to, operatives are advised*.
- **Formatting rule:** *"Never use markdown headings (#) or asterisks… Do not use dashes, hyphens, em-dashes or en-dashes anywhere in the output unless the user typed them in themselves. Never output placeholder text such as '[Your Company]', '[Insert Date]', 'TBC' or anything in square brackets."*
- **Header rule for compliance docs:** *"If this is a compliance, RAMS, COSHH, H&S or assessment document also include: REVIEW DATE: {review}"* → today + 12 months.
- **Profile block injection:** company name, address, contact, UTR, VAT, CIS status auto-populated from the user record.
- **Sign-off block injection:** RAMS is in `SINGLE_SIGNOFF_TOOLS`, so `_signoff_instructions` appends: *"End the document with a 'PREPARED BY' block containing: Full name, Role/title, Company name, Date, Signature. Do not put any placeholder text; if a value is missing leave it blank."*
- **Trade injection:** the profile block also contains the user's trade, which the LLM would use to weight examples.

### 3.4 Trade-specific prompt-level personalisation (front-end)
Because the AI never runs, trade personalisation is currently a purely-visual UI hint via `manual-handling-placeholders.js`. The placeholder is shown to the user only; it is not injected into the PDF unless the user types it in.

### 3.5 Prompt assembly order (would-be)
If `/api/generate` were called for RAMS:
1. System role opener + banned-word rules + formatting rules.
2. Document header rule (with `REVIEW DATE: {today+1y}`).
3. `AUTHOR PROFILE (use these exact values wherever a name, company, address, UTR, VAT or CIS reference is needed): <profile_block>`.
4. Sign-off instructions (single sign-off — Prepared by).
5. The legacy RAMS template from §3.2 as the user message.
6. `Today's date: {today}` and every form input as `- <field>: <value>` bullets.

## 4. Current Morris RAMS Specification (product spec)

*This section describes the RAMS document as Morris actually produces it today, independent of code. Another AI could rebuild the RAMS tool from this spec alone.*

### 4.1 Purpose
Generate a legally-defensible, site-ready Risk Assessment and Method Statement in "plain construction English" for UK trades operating on CDM-regulated sites. The output is an A4 PDF that a site manager, principal contractor or HSE inspector can accept without further editing, and that operatives can be briefed on.

### 4.2 Intended users
UK sole-trader tradesmen, subcontractors and small principal contractors. Ability level ranges from a duct fitter with no formal H&S authorship experience up to a working supervisor. The tool must not require the user to know consultant-grade H&S jargon; it produces the jargon on their behalf.

### 4.3 Document structure — canonical section order

1. **Document Control** — kv-table: Document Reference (auto `RAMS-YYYYMMDD-001`), Revision (default `Rev 1`), Issue Date (today), Review Date (today + 12 months), Prepared By (user's full name), Supervisor / Competent Person, Client, Principal Contractor, Site Address.
2. **Revision History** — table of every reissue (Rev, Date, Description, Author).
3. **Scope of Works** — Task, Estimated Duration, Number of Operatives, Work at Height (Yes/No), Overall Risk Rating (Low/Medium/High).
4. **Legislation** — fixed bulleted list (§4.9).
5. **Persons at Risk** — bulleted list from a fixed multi-select of {Site operatives, Site supervisor, Other trades, Members of the public, Visitors}.
6. **Training and Competence** — bulleted list from {CSCS, Manual Handling, Asbestos Awareness, PASMA, IPAF, Power Tool training, First Aid at Work}.
7. **Site Induction** — free-text paragraph. If the user leaves it blank, a sensible generic paragraph is used.
8. **Risk Matrix Key** — three sub-tables that explain the scoring system used throughout: (a) Likelihood 1–5 with plain-English meanings, (b) Severity 1–5 with plain-English injury outcomes, (c) Score → Rating → Action Required (1–6 Low / 7–14 Medium / 15–25 High with colour-coded rows).
9. **Risk Register Summary** — one-row-per-hazard summary table with Initial and Residual scores colour-filled in Green/Amber/Red.
10. **Hazard Detail and Control Measures** — for every hazard, a kv-block giving Exposure Route, Hazard/Substance, Activity, Persons Affected, Likelihood before, Severity before, Risk score/rating before, Likelihood after, Severity after, Risk score/rating after, followed by a bulleted list of Control measures.
11. **Control Measures and PPE** — bulleted list of ticked PPE plus (if used) an Override note explaining any deliberate omissions.
12. **Manual Handling** *(supplementary — appears only if filled)* — free-text describing typical loads, two-person lifts, HAV exposure limits, trade-specific weights.
13. **Noise and Vibration** *(supplementary — appears only if filled)* — free-text describing controls, hearing protection, HAV mitigation.
14. **Plant and Equipment** — bulleted list from {CAT & Genny, Step ladder, Mobile tower scaffold, MEWP, Cordless drill, SDS drill, Circular saw with extraction, Hand tools}. Always followed by the fixed sentence *"All plant and equipment listed above has been checked and is in date."*
15. **COSHH** — table of standard substances (Substance / Exposure / Activity / Controls). If any COSHH row is flagged as `licensedSeparate`, a distinct sub-section **15a. Substances Requiring a Separate Licensed Assessment** appears with a red STOP-WORK preamble.
16. **Permits and Authorisations** — states what this RAMS does *not* cover and mandates a separate permit or assessment before those activities can start. Boilerplate names: hot works, confined space, live electrical work, asbestos disturbance.
17. **Sequence of Operations** — numbered step-by-step method. If blank, prints "To be completed by supervisor before works start."
18. **Keeping the Site Tidy** *(supplementary — appears only if filled)* — free-text housekeeping and waste-segregation plan.
19. **Work at Height** — always prints. If WAH=Yes: standard paragraph referencing a separate Rescue Plan and stating harnesses must be in date and inspected daily. If WAH=No: "No work at height on this task."
20. **Welfare Arrangements** — kv-table (Toilets, Washing, Rest area, Drinking water).
21. **Environmental Considerations** — kv-table (Waste disposal, Dust and noise, Working hours, Spill management).
22. **Emergency Procedures** — kv-table (First Aider, Assembly point, Emergency number 999) + parsed contact table.
23. **Fire and Emergency Evacuation** *(supplementary — appears only if filled)* — free-text.
24. **Who This RAMS Has Been Shared With** *(supplementary — appears only if filled)* — Name / Company / Role table + reminder that all named operatives must acknowledge before starting work.
25. **Client / Principal Contractor Sign-Off** *(supplementary — appears only if any field present)* — Name, Role, Date + stamped client signature image.
26. **Reviewing This RAMS** *(supplementary — appears only if filled)* — free-text describing review triggers.
27. **Briefing and Sign-Off** — always prints. Blank Print Name / Signature / Date table sized to `max(6, operativesCount)` rows.
28. **Prepared By** *(not numbered)* — kv-block with Name / Role (defaults to "Director") / Company / Date, followed by the user's stamped signature image (150 × 56 pt).

### 4.4 Risk assessment methodology
- Scale: **1–5 Likelihood × 1–5 Severity = 1–25 Risk Score**.
- Bands: **Low ≤ 6, Medium 7–14, High 15–25**.
- Bands drive colour: Green / Amber / Red.
- Every hazard has both an *initial* and a *residual* score, and the difference must be justified by the entered controls.
- Residual **severity** cannot be lowered below the initial severity without an explicit user confirmation (`window.confirm`) — controls generally lower likelihood, not severity, unless the control physically removes the consequence (e.g. isolation removes the electricity).

### 4.5 Hazard methodology
Each hazard is described using three orthogonal fields: **exposure route**, **hazard/substance name** and **activity causing exposure**. These are combined by a deterministic translator (`composeHazardLine`) into a plain-language sentence — e.g. *"Breathing in MDF dust while cutting mdf with a circular saw."* — so the document never sounds like a template.

### 4.6 Control measures
Free-text, one control per line, rendered as a bulleted list. The tool encourages plain wording via placeholder examples (*"Use M-class extraction on the saw."*).

### 4.7 PPE guidance
- User picks from a fixed set: {Hard hat, Safety boots, Hi-vis vest, Safety glasses, Gloves (cut-resistant), Gloves (chemical), RPE — dust mask or respirator, Hearing protection, Harness and lanyard, Knee pads}.
- The tool cross-checks the hazards against `PPE_RULES` and highlights any missing item with a gold suggestion pill plus the reason (e.g. "Dust or cutting in the air" → RPE). Users must either tick the suggested PPE or supply an override note before the PDF will export.

### 4.8 Emergency arrangements
Mandatory fields: First Aider on site, Assembly point. Standard `999` is always printed. Users can supply additional Role : Number lines, which the renderer parses into a two-column table.

### 4.9 Legal references (always cited)
- Management of Health and Safety at Work Regulations 1999
- Manual Handling Operations Regulations 1992
- COSHH Regulations 2002
- PUWER 1998
- Personal Protective Equipment at Work Regulations 1992
- Work at Height Regulations 2005
- Control of Noise at Work Regulations 2005
- CDM 2015

### 4.10 Environmental considerations
Waste disposal, Dust and noise, Working hours, Spill management — all free-text kv fields.

### 4.11 Review dates
Standard review interval **12 months** from issue. Printed on page 1 (Document Control) and — if filled — the user's own review-trigger paragraph in section 26. Backend adds `today+1y` to `saveToolData` for future alerting.

### 4.12 Signature requirements
- **Prepared by** — mandatory. Full name from profile plus a signature (either drawn live on this page or reused from the profile). The tool blocks export if both are missing.
- **Client / Principal Contractor sign-off** — optional. If any of Name / Role / Date / Signature is present, the block is rendered and the client signature image (if drawn) is embedded.
- **Briefing sign-off** — printed as a blank table for wet-signatures on-site, sized to at least 6 rows and never fewer than `operativesCount`.

### 4.13 Personalisation
Auto-populated from the user profile:
- `fullName` → Prepared by, Revision author.
- `companyName` → Header (uppercase, top-right of every page) and Prepared-by block.
- `companyLogo` → Header logo (or Morris "M" mark if absent).
- `signature` (base64 PNG) → Prepared-by signature stamp.
- `signatureRole` → Prepared-by Role (defaults to "Director").
- `trade` → Manual Handling section placeholder ("Personalised for {trade}" pill).

### 4.14 Trade-specific behaviour
Manual Handling placeholder examples change per trade (Duct Fitter, Electrician, Plumber, Heating Engineer, Bricklayer, Groundworker, Carpenter and Joiner, Plasterer). All other content is trade-neutral. Trade also drives Dashboard visibility (RAMS is in the top-3 recommended tools for every trade in `trade-recommendations.js`).

### 4.15 Writing style
- **Plain construction English.** Short sentences. Active voice. No consultant phrases. No em-dashes/en-dashes.
- Numbered lists for methods. Bulleted lists for hazards, PPE, equipment.
- Every hazard sentence is generated deterministically by `composeHazardLine` — same input always produces the same wording, so two RAMS for the same activity read consistently.

### 4.16 Tone of voice
Confident, practical, protective. Written *for* the tradesman *by* the tradesman. Warnings are direct ("STOP — the following substances need a separate licensed assessment before work starts"), not padded.

### 4.17 Formatting rules
- A4 portrait, Helvetica.
- Gold accent rule under the header on every page.
- Sequential section numbering (`1.`, `2.`, `3.` …) with sub-numbering `Na.` for STOP-work variants.
- Every table has real borders, header rows are gold-tinted.
- Risk band cells are colour-filled: Green / Amber / Red.
- Signatures stamped as real 150 × 56 pt images, not typed names.
- Footer on every page: `Ref · Date · User` + Morris attribution + `ICO C1923529`.

## 5. Quality Review — Where the Tool Could Be Improved

### 5.1 Missing sections vs. professional UK RAMS practice
| # | Missing | Impact |
|---|---|---|
| M1 | **First-page cover / signature strip acknowledging every RAMS reviewer** | Professional RAMS packs typically have a dedicated cover page showing document title, project, contractor, principal contractor, revision, and a "Reviewed by" signature line separate from Prepared By. |
| M2 | **Risk Assessment methodology *statement*** | Section 8 shows the *key* but never states the method itself in words (e.g. "This RAMS uses a semi-quantitative 5×5 matrix as per HSE guidance INDG163…"). |
| M3 | **First aid arrangements detail** — nearest A&E name and address, distance to hospital, treatment room location on site. Currently only First Aider name + assembly point + 999 are captured. |
| M4 | **RIDDOR reporting statement** — obligation to report specified injuries, dangerous occurrences and over-7-day injuries. Not mentioned anywhere. |
| M5 | **Lone working / buddy system** — absent even for tools/trades where it's routine. |
| M6 | **Site rules / PPE-on-site policy** — commonly a paragraph at the front of professional RAMS. |
| M7 | **Weather and lighting** — no field for temperature limits, high-wind cutoff for WAH, lighting for early/late works. |
| M8 | **Traffic management / vehicle movements** — no dedicated section. |
| M9 | **Interfaces with other trades** — "Persons at Risk" is bulleted but there's no field for *how* concurrent operations are coordinated. |
| M10 | **Young persons / apprentices / new & expectant mothers** — statutorily required consideration under MHSW 1999 Reg 3, absent. |
| M11 | **Mental health / fatigue / working hours** — nothing beyond the environmental "Working hours" free-text. |
| M12 | **Pre-start checklist** — walkaround, permit checks, harness inspection tickbox. Currently referenced only for WAH. |

### 5.2 Weak / repeated content
| # | Issue |
|---|---|
| W1 | The **Legislation** block is a hard-coded 8-statute list. It should be filtered by scope — a joinery RAMS with no COSHH shouldn't cite COSHH; a non-WAH RAMS shouldn't cite Work at Height Regulations 2005. |
| W2 | **"Plant and Equipment"** always prints *"All plant and equipment listed above has been checked and is in date."* — the assertion is unsupported. Should be conditional on a user-ticked confirmation and ideally reference a PAT / inspection register. |
| W3 | **Work at Height** paragraph is boilerplate: *"harnesses must be in date and inspected on the day"* — but the tool never captures the inspection method, the anchor points or who the trained rescuer is. |

| W5 | The **Site Induction** default paragraph is generic ("covers site rules, hazards, welfare arrangements, emergency procedures and points of contact"). Real inductions vary by site. |
| W6 | The **Briefing and Sign-Off** table always allocates at least 6 rows even when `operativesCount = 1`. That's wasteful and looks unfinished. |
| W7 | The **Prepared by** block defaults `Role` to "Director" — meaningless for sole traders or subbies. Should default to nothing and be user-configurable in the profile. |
| W8 | **Revision History** is not enforced — the user can issue *"Rev 2"* while leaving a `Rev 1` row with `description: "Initial issue"`. No integrity check that revisions actually differ. |
| W9 | **COSHH** table only captures 4 columns (Substance/Exposure/Activity/Controls). Missing: WEL (workplace exposure limit), route of entry timing, first-aid measures per substance, disposal. |

### 5.3 Weak / thin prompts (legacy template)
Because the AI is not actually used at runtime, these are theoretical, but they matter if `/api/generate` is ever re-enabled for RAMS:
| # | Issue in `tools-config.js` l.111–127 |
|---|---|
| P1 | The prompt says "produce a row per hazard" but never explains how to *derive* Likelihood and Severity if the user didn't supply them. A weak LLM will just pick 3/3. |
| P2 | The prompt uses the phrase "risk-rated row" but the app's real matrix is Green/Amber/Red — the LLM has no colour cue. |
| P3 | "leave a placeholder line stating 'To be completed by supervisor before works commence.'" — the codebase's global rule bans placeholder text; the two rules conflict. |
| P4 | Says "Also list every emergency contact number supplied by the user in a clean two-column table" — but the app never sends an *emergency contacts array*; only a free-text lump. An LLM would produce inconsistent tables. |
| P5 | "Close with a 'PREPARED BY' block … and a 'REVIEWED BY' block." — the runtime PDF has no Reviewed By block, so the spec and the actual output diverge. |
| P6 | Sequence of Operations tells the LLM to produce the *user's* text as a numbered list. That is fine, but the prompt gives no fallback if the user supplied a paragraph rather than steps — the LLM will hallucinate the split. |

### 5.5 Missing HSE guidance / legislation references
- No reference to **HSE INDG163** ("Five steps to risk assessment") which is the standard authority for the L×S method.
- No reference to **HSG150** (Health and safety in construction), **HSG65** (Managing for health and safety) or **CDM 2015 Approved Code of Practice L153**.
- No reference to **Reg 3 of MHSW 1999** (specific consideration of young persons, new/expectant mothers).
- No reference to **Regulation 4 of CDM 2015** (client duties) or **Regulation 8** (competence) — relevant when the RAMS is issued *to* a PC.
- No reference to **CAR 2012** (asbestos) despite the tool exposing an "asbestos" default in `notCovered`.
- Noise / vibration section doesn't mention **Lower Exposure Action Value (80 dB(A) / EAV of 2.5 m/s²)** or **HAV daily exposure limit value (5 m/s²)**.
- Manual Handling section doesn't cite the **HSE MAC Tool** or the **16 kg / 25 kg guidance weights**.

### 5.6 Missing construction best-practice
- No **method-statement dependency check** — e.g. if `workAtHeight = true`, the app doesn't force a link to the Working at Height Rescue Plan tool (though it references it in text).
- No **link out to the user's other Morris outputs** — the RAMS could cross-reference Toolbox Talks, COSHH Assessments, Noise Assessments already generated in the app.
- No **language check** for the sequence steps: nothing prevents a step like "Start work carefully."
- No **QR code / digital acknowledgement** — operatives can only sign wet.
- No **change-control** — if the user re-exports after editing, the previous version is not automatically archived or versioned.
- No **document ID uniqueness** — `RAMS-YYYYMMDD-001` can collide if the user exports twice in a day.

### 5.7 Integration gaps
- **`saveToolData("rams", …)`** writes review dates the alerts engine never reads (`alerts.js` only scans `rams-library`). The one-off "review due" notification never fires for standalone RAMS docs.
- **Document History** is never populated (no `/api/documents/save` call). If the user clears their browser downloads, the RAMS is lost.
- **No email/WhatsApp/SMS actions** on the RAMS page — the standard `ToolHeader` action bar (Save / Copy / PDF / Email / WhatsApp / SMS) is not rendered.
- **`saveToolData("rams-library", …)`** — a completed RAMS could seed the RAMS Library register automatically, but doesn't.

### 5.8 UX / validation gaps
- The **PPE mismatch guard** only checks for missing suggestions, not for *contradictory* selections (e.g. Harness ticked with no WAH hazard).
- **`personsAtRisk` and `training`** cannot be extended — they are hard-coded arrays.
- The **hazard row** allows L/S = blank (via `clamp` returning `""`), which then renders as "0 —" in the badge and no rating band. That's silent failure.
- The **residual severity override** flag (`severityManualOverride`) is stored but never printed on the PDF, so an inspector can't tell whether a lowered severity was reasoned or accidental.

## 6. Summary — How the Morris RAMS Tool Actually Works Today

- **UI:** one dedicated React page (`Rams.jsx`, 1031 lines) with 23 form sections, live risk scoring, PPE/equipment auto-suggestion, dual-signature capture, draft save/resume and a strict pre-export validation gate.
- **PDF:** rendered 100 % client-side by `rams-pdf.js` (652 lines) using jspdf. Real bordered tables, colour-coded risk bands, auto-numbered sections, standard Morris header/footer branding.
- **AI:** none. A legacy Claude prompt still lives in `tools-config.js` but is unreachable from the UI. Trade personalisation is purely UI hint (`manual-handling-placeholders.js`).
- **Persistence:** the finished PDF is *only* saved to the user's Downloads folder. Drafts persist server-side via `/api/drafts`. A local record is written to `localStorage` for alerts, but the alerts scanner reads a different key and never fires for standalone RAMS.
- **Compliance basis:** eight statutes always cited, HSE-derived 5×5 matrix, single Prepared By signature required, dual Client sign-off supported. Missing several important regs (CAR 2012, MHSW Reg 3, HAV/EAV limits) and several professional-RAMS sections (First Aid detail, Traffic Management, Young Persons, RIDDOR).
- **Biggest gap:** the RAMS does not enter Document History, does not seed the RAMS Library, and its review-due date never triggers a notification. Everything after "Download" is invisible to the rest of the app.
